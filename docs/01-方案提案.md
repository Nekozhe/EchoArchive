# 期末大作业方案提案 v0.1（主题一 · 剧本杀结构）

> 状态：**待确认**。本文是设计提案，不是最终需求说明书。所有案件、人物、线索均为原创设定，仅借鉴剧本杀的**机制结构**。

---

## 0. 一句话

一个**单机校园推理 App**：玩家受委托调查一起实验室原型机失窃案，在 3 个场景中探索取证、盘问 4 名关系人、把线索放进推理槽验证假设，最终指认嫌疑人并进入 3 种结局之一；全程进度可存档、杀进程后能恢复。

暂定作品名（三选一，可换）：
- 《回声档案》
- 《第七节课的空位》
- 《23:47 的门禁》

---

## 1. 为什么用剧本杀结构（以及边界）

老师的流程描述本身就是剧本杀骨架。对应关系：

| 剧本杀环节 | 本作品的 App 功能 | 对应评分项 |
|---|---|---|
| 剧本背景 / 世界观 | 开场委托页 + 案件简报 | 项目简介、需求分析 |
| 人物本 | 4 张嫌疑人档案卡（动机 / 时间线 / 秘密） | 数据建模 |
| 搜证 | 场景热点探索，点对位置获得线索卡 | 核心功能、交互 |
| 线索卡 | `Clue` 对象（名称/描述/关联人物/关联地点/是否关键/是否已获得） | 数据与状态分析 |
| 盘问 | 对话树 + "出示线索"解锁新对话 | 条件分支 |
| 推理 / 投票 | 线索板：人物槽 + 时间槽 + 物证槽，组合校验 | 核心业务规则、单测 |
| 结局 / 复盘 | 3 种结局 + 推理回顾页 | 结局分支 |
| 存档 | 中途退出、杀进程、恢复进度 | 持久化 9 分 |

**版权边界**：只借机制与 UI 范式，案件/人物/台词全部原创。报告中注明"参考剧本杀的三要素推理结构"即可，不引用任何具体剧本内容。

## 2. 玩法设计

### 2.1 核心循环

```
接委托 → 选场景 → 点热点取证 → 线索入库 → 用线索解锁对话/新场景
      → 线索板组假设 → 校验 → 指认 → 结局 → 复盘
```

### 2.2 案件设定（校园现实向 + 轻悬疑）

- **时间**：期末答辩前夜，23:00–次日 07:00
- **事件**：物联网竞赛原型机在 302 实验室失窃，机箱被弃于天台，主板不见
- **玩家身份**：受辅导员委托的"临时调查员"（同班同学，非老师，所以没有强制权限 → 天然的"权限门控"设计理由）
- **4 名关系人**

| 代号 | 身份 | 表面动机 | 真实秘密 |
|---|---|---|---|
| A | 队友（负责硬件） | 与死者…（无死者，改为）与玩家有过项目分工争执 | 私下买过二手主板 |
| B | 队友（负责代码） | 答辩前想退出 | 当晚在实验室，但怕被追责而隐瞒 |
| C | 实验室管理员 | 门禁被刷却未上报 | 那晚忘锁门，怕担责 |
| D | 隔壁班竞争者 | 竞赛直接对手 | 只是来偷看方案，没偷机器 |

> 真凶建议：**A**（动机：原型机核心板是他私换的劣质板，怕答辩暴露）。C 和 D 是红鲱鱼。

### 2.3 三个场景 + 14 个事件节点

| # | 场景 | 事件节点 | 触发条件 | 产出 |
|---|---|---|---|---|
| 1 | 委托页 | 接受委托 | 无 | 进入第一幕 |
| 2 | 302 实验室 | 检查工作台 | 无 | 线索①电源线切口 |
| 3 | 302 实验室 | 查看门禁面板 | 无 | 线索②刷卡记录 |
| 4 | 302 实验室 | 翻看垃圾桶 | 无 | 线索③快递单 |
| 5 | 值班室 | 与管理员 C 对话 | 无 | 对话，可出示②解锁 |
| 6 | 值班室 | 调看监控回放 | 持有②且 C 信任≥1 | 线索④监控离线时段 |
| 7 | 走廊 | 查看消防通道 | 持有④ | 线索⑤拖拽痕迹 |
| 8 | 走廊 | 与队友 B 对话 | 无 | 对话 |
| 9 | 走廊 | 出示外卖小票给 B | 持有⑥ | 线索⑦B 的时间线矛盾 |
| 10 | 天台 | 搜索水箱后侧 | 持有⑤ | 线索⑧机箱外壳 |
| 11 | 天台 | 与队友 A 对质 | 持有③或⑧ | 对话，A 开始狡辩 |
| 12 | 推理台 | 首次解锁线索板 | 线索≥4 | 开放推理槽 |
| 13 | 推理台 | 提交假设（错误可重试） | 线索板非空 | 校验反馈 |
| 14 | 结局 | 最终指认 | 至少一次校验通过 | 进入对应结局 |

> 14 ≥ 题目要求的 12；其中 9、11 是"线索真实改变后续"的证据点，不是文字跳转。

### 2.4 线索表（8 条，≥ 要求 6 条）

| ID | 名称 | 关键 | 关联 | 用途 |
|---|---|---|---|---|
| C1 | 被剪断的电源线 | 否 | 302 / 手段 | 提示需要工具 |
| C2 | 门禁刷卡记录 23:47 | 是 | C / 时间 | 解锁监控 |
| C3 | 二手主板快递单 | 是 | A / 动机 | 指向 A |
| C4 | 监控 23:00–24:00 离线 | 是 | 环境 / 时间 | 缩小时间窗 |
| C5 | 消防通道拖拽痕 | 否 | 走廊 / 路径 | 指向天台 |
| C6 | 外卖小票 23:30（B 署名） | 是 | B / 时间 | 洗清或牵出 B |
| C7 | 焊点粗糙的主板残片 | 是 | A / 物证 | 关键物证 |
| C8 | 天台机箱外壳（缺主板） | 否 | 天台 / 地点 | 确认失窃方式 |

### 2.5 推理槽与结局判定

**推理槽**：人物（A/B/C/D） + 时间段（23:00–23:40 / 23:40–00:20 / 00:20–07:00） + 关键物证（C3/C4/C6/C7）

**判定函数（纯函数，可直接单测）**：

```
judgeDeduction(slots, ownedClues) -> { ok, endingId, reason }
```

| 结局 | 条件 | 名称 |
|---|---|---|
| E1 真相结局 | 人物=A ∧ 时段=23:40–00:20 ∧ 物证=C7 | 《焊点》 |
| E2 半真相 | 人物=A ∧ 其余任一错 | 《指认对了，但证据链断了》 |
| E3 误判结局 | 人物≠A | 《替罪羊》 |

> 题目要求 ≥2 个由不同条件触发的结局，这里做 3 个。

## 3. 技术方案

### 3.1 页面清单（6 页）

| 页面 | 职责 | 关键 ArkUI 技术 |
|---|---|---|
| `Index` 委托页 | 开场、继续游戏、开新档 | `@State`、`animateTo` 入场 |
| `ScenePage` 场景探索 | 热点图 + 事件节点列表 | `Stack` 叠层、`Button` 热区、`List` |
| `ClueBoard` 线索板 | 线索卡网格、点选、详情弹层 | `Grid`、`@State` 选中态、`bindSheet` |
| `DeductionPage` 推理台 | 三槽位、提交、反馈 | 点选式放置（不做拖拽）、`@Watch` 校验 |
| `DialogPage` 对话 | 对话树、出示线索 | `List` 滚动、条件渲染 |
| `EndingPage` 结局 + 复盘 | 结局文案、推理回顾、重开 | `animateTo`、路由返回 |

### 3.2 数据模型

| 对象 | 关键字段 | 存储 |
|---|---|---|
| `Clue` | id, name, desc, key, owner, sceneId, owned | 静态常量表 |
| `EventNode` | id, sceneId, title, requireFlags, grantClues, effects | 静态常量表 |
| `Npc` | id, name, role, motive, secret, trust | 静态表 + 存档内 trust |
| `DeductionSlots` | person, period, evidence | 运行时 + 存档 |
| `GameState` | act, ownedClues[], visitedScenes[], flags{}, trust{}, deductions[] | 存档主体 |
| `SaveMeta` | slotId, updatedAt, actLabel, progress | 存档索引 |

持久化：**Preferences**（key-value JSON 序列化）为主；若想加分，线索表/事件表改用 **RDB**（关系型），报告里就能写"静态内容与玩家进度分离存储"的理由。

### 3.3 单元测试设计（5 条，覆盖三类）

| # | 类别 | 输入 | 预期 |
|---|---|---|---|
| T1 | 正常 | A + 23:40–00:20 + C7，线索齐全 | E1 |
| T2 | 边界 | A + 正确时段 + C4（物证错） | E2 |
| T3 | 边界 | 空槽提交 | 拒绝，提示"假设不完整" |
| T4 | 异常 | 放入未获得的线索 C7 | 拒绝，不进入判定 |
| T5 | 异常 | 存档 JSON 缺字段/版本号不匹配 | 降级为初始状态，不崩溃 |
| T6 | 可选 | 门控：无 C2 时调监控 | 返回"权限不足" |

### 3.4 状态管理与关键用法

- `@State` 存页面态，`@Provide/@Consume` 或 `AppStorage` 存全局 `GameState`
- `@Watch` 监听线索数量变化 → 自动刷新线索板与推理台可用性
- `animateTo` 做线索卡入场、结局页淡入
- 存档触发点：每次获得线索 / 切换场景 / 提交假设后

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 文案写不完（最大风险） | 所有剧情数据放常量表/JSON，页面只做渲染；先写"能跑通的最短文本"，W5 再润色 |
| 被判定"只做文字跳转" | 每个事件节点必须绑定一个"前置条件 + 产出物"，报告里用表格证明 |
| 线索板交互做复杂了 | 用点选放置，不做自由拖拽；拖拽留给主题二 |
| 结局条件写死 | 判定抽成纯函数 + 配置文件（后期改结局不用改页面） |
| 存档结构后期要改 | 存档带 `schemaVersion` 字段，为 T5 用例做准备 |
